# CORE-AI project audit

This audit covers the repository’s workstation UI, Python API, PostgreSQL migrations, model adapter, task worker, webhooks, Ubuntu release scripts, and CI. Findings are based on source and local checks. Production configuration, network exposure, deployed service health, and real model performance require verification on the target workstation.

| Priority | Area | Finding | Recommended work |
|---|---|---|---|
| High | Shared inference capacity | API jobs, chat replies, and agent tasks share one inference slot and one 20-item admission limit. A connection can currently use all 20 slots. [Admission and worker](../backend/src/core_ai/runs.py) | Add configurable workspace and per-connection quotas with fair queueing. Retain the single-worker preset for constrained hosts. |
| High | API job operations | Clients can submit and read jobs, and webhooks can report completion. Generic connection jobs have no dedicated cancellation endpoint or operator action. The project task cancellation path requires both a project and agent. [Connections](../backend/src/core_ai/connections.py) · [Task API](../backend/src/core_ai/api.py) | Add permission-scoped cancel and retry for connection jobs, without coupling them to projects or agents. |
| High | Recovery and audit retention | The documented backup test restores to a temporary database on the same host. The default script stores database and private configuration snapshots together. There is no repository-defined off-host schedule, restore objective, or independent audit retention. [Deployment](../scripts/deploy-workstation.py) | Define retention and recovery targets, verify an off-host restore, and protect access to configuration and database backups separately. Add an audit export target. |
| Medium | Connection credentials | The previous release stored hashes only and required opening details to find Edit. Version 1.9 adds direct View key and Edit actions, opt-in encrypted recovery, password confirmation, and audited reveals. Earlier hashes remain usable and can be rotated when recovery is needed. [Connections API](../backend/src/core_ai/connections.py) · [UI](../ui/src/Connections.tsx) | Add independent rotation and monitoring for the recovery key itself. Evaluate managed key storage where the installation requires it. |
| Medium | Connection ownership | Bearer authorization depends on the individual administrator who created the connection remaining active and an administrator. [Connection authentication](../backend/src/core_ai/connections.py) | Add dedicated service identities, explicit transfer of ownership, and scoped operator roles. Preserve direct personal and project-linked keys. |
| Medium | Webhook operations | Delivery retries are bounded and recorded, but the UI shows delivery state only. There is no manual replay or provider-independent endpoint test. [Webhook worker](../backend/src/core_ai/webhooks.py) | Show last attempt time and a sanitized failure category, add test delivery and audited replay, and preserve authenticated HTTP use without webhooks. |
| Medium | Projects and knowledge | The project library has membership, instructions, file and source revisions, and lexical retrieval. Retrieval uses fixed excerpt limits and PostgreSQL text search. [Chat context](../backend/src/core_ai/chat.py) · [Worker context](../backend/src/core_ai/worker.py) | Add configurable retrieval limits and optional semantic search, with per-answer source visibility. Preserve lexical search as an available choice. |
| Medium | Chats, artifacts and files | Chat history, event lists, files and artifacts have fixed server-side windows without cursor paging. Chat has a 200-message cap, and document ingestion is format-limited. [Chats](../backend/src/core_ai/chat.py) · [Files](../backend/src/core_ai/files.py) · [Artifacts](../backend/src/core_ai/workspace.py) | Add paging and filters. Make long-chat continuation easy, and provide optional, capability-gated OCR and additional file formats. |
| Medium | Models and providers | The inference path is Ollama-oriented and sends a fixed 8,192-token context setting. Local provider capability inspection is implemented. [Models](../backend/src/core_ai/models.py) · [Chat execution](../backend/src/core_ai/chat.py) | Expose model-specific context and timeout presets, measured capability status, and optional provider adapters. Retain local-only operation as a supported profile. |
| Medium | Integration contract | REST examples and signed webhooks are available. Public OpenAPI generation is disabled and the legacy integrations response always returns an empty list. [API](../backend/src/core_ai/api.py) | Publish a versioned machine-readable automation contract and connect the integrations summary to authorized configuration. Keep existing API routes backwards compatible. |
| Medium | Operations and scale | UI refresh uses periodic polling. Worker recovery and heartbeat exist, but the repository has no deployment-specific alerting thresholds, workload performance baseline, or error budget. [Refresh loop](../ui/src/App.tsx) · [Worker](../backend/src/core_ai/worker.py) | Add queue-latency and webhook-failure visibility, alerting, and load checks against the intended hardware. Consider push updates for active jobs. |
| Roadmap | Workflows, multimodal, repository execution, and identity | Scheduled workflows, hosted search, broader multimodal support, isolated repository execution, and external identity are advertised as planned or outside the current implementation. [Capabilities](../backend/src/core_ai/workspace.py) | Add these as opt-in capabilities with explicit permissions, activation, and limits. Keep discovery available and show why a capability is inactive. |
| Roadmap | Responsive and release quality | CI covers unit, database, dependency and native installer checks. It does not run the manually exercised Chromium breakpoint flows. The build also emits a large-chunk warning. [CI workflow](../.github/workflows/checks.yml) | Add browser checks for mobile and keyboard navigation, and measure route-level bundle splitting. |

The encrypted-recovery design uses the host OpenSSL package, RSA-OAEP with SHA-256, a private key held in the workstation environment, password confirmation using the account lockout policy, and an audit event for each successful reveal. The normal list returns only recoverability status. A host or backup that exposes both ciphertext and private configuration can reveal the stored credential. See the [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) and [OpenSSL pkeyutl documentation](https://docs.openssl.org/3.0/man1/openssl-pkeyutl/).


## Implementation status in 1.10.0

| Audit area | Delivered | Still open |
|---|---|---|
| Shared capacity | Configurable workspace reserve, alternating queue dispatch, independent bounded file extraction | Production throughput baseline and multi-worker/provider capacity |
| API operations | Dynamic all-model access, per-model policies, separate text embedding permission, usage, scoped cancellation and retry, automation OpenAPI | Additional specialty operations and provider adapters |
| Key operations | Optional rotation overlap and early expiry | Service identities, ownership transfer, independent recovery-key rotation |
| Webhooks | Audited replay with the original event ID | Test delivery, sanitized failure categories and operator alerts |
| Source integrity | Atomic creation/deletion and audit events, ranked lexical chat retrieval, source version IDs in use events | Citation and version visibility in the UI, tunable retrieval and semantic indexing |
| Runtime operations | Authenticated database/worker/provider readiness and configured integration summary | Alerting thresholds, retention and independent audit export, off-host restore verification |
| Workbench | Responsive model access and usage controls | Cursor pagination across library modules, broader OCR/multimodal support, browser CI, route splitting and opt-in capabilities |

Migration `010_model_usage_controls.sql` preserves 1.9 key scope, defaults and permissions. The new worker should be live before enabling embedding jobs. Before an intentional rollback to 1.9 after using the new controls, pause affected connections and drain or cancel queued embedding jobs. Review each connection’s effective policy before enabling it on an older release. A 1.9 runtime does not enforce the 1.10 model policy fields or process the embedding operation.
